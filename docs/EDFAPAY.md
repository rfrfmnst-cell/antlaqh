# مبسط / EdfaPay — الدفع الإلكتروني

الحالة في الإصدار 5.7.0: المنصة تدعم إنشاء صفحة دفع مستضافة لدى EdfaPay من
الخادم، إلى جانب التحويل البنكي. لا تدخل بيانات البطاقة إلى خادم انطلاقة.
رجوع العميل إلى رابط النجاح لا يُعتبر إثبات تحصيل؛ يعتمد مسار المراجعة على
Webhook الموقّع وسجل مزوّد الدفع.

## التفعيل الآمن

ابدأ ببيئة EdfaPay التجريبية وحساب الاختبار. لا تفعّل الإنتاج قبل نجاح إنشاء
جلسة دفع، الإلغاء/الفشل، وWebhook الموقّع.

اضبط القيم التالية في بيئة تطبيق Node.js الخاصة على Hostinger، ولا تحفظ أي قيمة
سرية في Git أو الصور أو المحادثات:

- `APP_URL=https://antlaqh.com`
- `EDFAPAY_CHECKOUT_ENABLED=true`
- `EDFAPAY_API_KEY=<private server API key>`
- `EDFAPAY_INITIATE_URL=<endpoint supplied for the active EdfaPay environment>`
- `EDFAPAY_WEBHOOK_ENABLED=true`
- `EDFAPAY_WEBHOOK_SECRET=<same private webhook secret configured in EdfaPay>`

في الإنتاج، نقطة إنشاء الدفع الحالية هي
`https://app-api.edfapay.com/api/v1/payment-gateway/initiate`. مفتاح API يرسل
من الخادم فقط في `X-API-KEY`، ولا يظهر في `/api/config` أو لوحة الإدارة أو
استجابة إنشاء الجلسة.

## مسار العميل

1. ينشئ العميل الطلب ويختار الإضافات.
2. يراجع العقد ويوافق على الإصدار الحالي.
3. عندما تصبح حالة الطلب `awaiting_payment` يستطيع اختيار:
   - الدفع الإلكتروني عبر مبسط / EdfaPay، إذا كان الربط جاهزًا.
   - التحويل البنكي وإرفاق الإيصال.
4. طلب `POST /api/orders/:id/payment-session` ينشئ مرجعًا جديدًا خاصًا بمحاولة
   الدفع ويستخدم مبلغ الطلب المحفوظ على الخادم، وليس مبلغًا يرسله المتصفح.
5. يعيد الخادم `redirectUrl` تحت نطاق EdfaPay فقط، ثم ينتقل العميل إلى صفحة
   الدفع المستضافة.
6. عند الرجوع إلى `/#/payment/:id` تعرض المنصة نتيجة الرجوع فقط، ولا تغيّر
   حالة الدفع من الرابط.

## Webhook الموقّع

المسار هو:

`POST https://antlaqh.com/api/webhooks/edfapay`

عند وجود `EDFAPAY_WEBHOOK_SECRET` تتحقق المنصة من
`X-EdfaPay-Signature` باستخدام HMAC-SHA256 على جسم الطلب الخام قبل تحليل JSON.
يجب أن يعيد الاستقبال الناجح HTTP 200 والنص `OK`.

يحفظ سجل المراجعة معرف العملية، مرجع محاولة الدفع، المبلغ، رمز العملة، الحالة،
نوع العملية، معرف التاجر وRRN فقط. لا يحفظ رقم البطاقة أو token البطاقة أو جسم
الطلب الخام أو مفاتيح الربط.

يدعم `EDFAPAY_CALLBACK_TOKEN` مؤقتًا كتوافق مع الربط القديم فقط عندما لا يوجد
Webhook Secret. الربط الموقّع هو الخيار المفضل.

## المطابقة والتأكيد

كل جلسة دفع تحفظ محليًا في `edfapayAttempt` بمبلغ الطلب ومرجعه. عندما يصل
Webhook، تعرض لوحة `/#/admin/payments` إن كان مرجع المزوّد مطابقًا لجلسة طلب
معروفة والمبلغ المتوقع.

حتى يكتمل اختبار دورة التسوية في حساب مبسط الفعلي، يبقى تأكيد التحصيل يدويًا
من الإدارة. لا يؤدي Webhook وحده إلى تغيير `payment.confirmed`، ولا يمنح
تنزيل منتج رقمي. هذا يمنع تأكيد دفعة بسبب redirect مزور أو إشعار غير مطابق.

## الاختبار قبل الإنتاج

اختبر على الأقل:

1. إنشاء جلسة بالقيمة الصحيحة من عقد مقبول.
2. رفض إنشاء جلسة قبل قبول العقد أو لطلب مدفوع.
3. أن المتصفح لا يرى `EDFAPAY_API_KEY` أو `EDFAPAY_WEBHOOK_SECRET`.
4. Webhook صحيح التوقيع يصل ويظهر في لوحة المدفوعات.
5. توقيع خاطئ يُرفض ولا يحفظ سجلًا.
6. الإشعار المكرر لا ينشئ سجلًا ثانيًا.
7. رابط النجاح لا يؤكد الدفع من تلقاء نفسه.
8. مطابقة رقم محاولة الدفع والمبلغ مع الطلب قبل أن تؤكد الإدارة التحصيل.

بعد نجاح هذه الاختبارات في Sandbox، استخدم مفتاح الإنتاج ونقطة الإنتاج، ثم نفّذ
عملية حقيقية منخفضة القيمة ومراجعة التسوية في لوحة EdfaPay قبل اعتماد القناة
لجميع العملاء.
